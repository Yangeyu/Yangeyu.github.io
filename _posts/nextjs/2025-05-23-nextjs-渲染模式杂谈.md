## **渲染模式**

### **1. 客户端渲染 (Client-Side Rendering - CSR)**

- **定义与工作原理：**
    - 传统的 React 应用模式 (例如 Create React App 创建的应用)。 
    - 浏览器下载一个最小的 HTML 文件，然后通过 JavaScript 下载、解析并执行，最终在浏览器中渲染出页面内容。 
    - 在 Next.js 中，你仍然可以在组件内部使用 useEffect 配合 fetch (或 SWR, React Query) 来实现 CSR，尤其是在预渲染的页面加载后，需要获取用户特定或频繁更新的数据时。
     
- **优点：**
    - 丰富的用户交互体验。
    - 页面加载后，后续导航通常很快（如果代码分割做得好）。
    
- **缺点：**
    - **SEO 不佳：** 搜索引擎爬虫可能无法很好地执行 JavaScript，导致难以索引内容。 
    - **初始加载性能差：** 用户需要等待所有 JavaScript 下载并执行完毕才能看到内容，可能导致较长的白屏时间 (FCP, LCP 指标差)。
    
- **Next.js 中的使用场景：**
    - 用户仪表盘 (Dashboard) 等需要高度交互且对 SEO 要求不高的私有页面部分。
    - 在 SSG/SSR 页面加载后，动态加载非关键性、用户特定的内容。
	
- **实践 (app 目录)**
```tsx
"use client"
...
```
### **2. 静态站点生成 (Static Site Generation - SSG)**

- **定义与工作原理：**
    - HTML 在**构建时 (build time)** 生成。
    - 每次构建，所有使用 SSG 的页面都会生成对应的 HTML 文件。这些 HTML 文件可以被 CDN 缓存，提供极快的加载速度。
    - 如果页面需要外部数据来渲染，可以直接在 `app/` 目录中的 `page.js` 文件中使用 `async` 函数进行数据获取。此操作将在构建时执行，并用于生成静态内容。
    - 对于动态路由（如 `app/blog/[id]/page.js`），可以使用 `generateStaticParams` 函数来告诉 Next.js 哪些路径需要在构建时生成页面。该函数返回所有动态参数的数组，Next.js 会据此生成对应的静态页面。
     
- **优点：**
    - **极佳的性能：** HTML 已生成并可被 CDN 缓存，加载速度非常快。
    - **良好的 SEO：** 搜索引擎可以直接抓取到完整的 HTML 内容。
    - **降低服务器负载：** 因为内容是预先生成的，不需要服务器在每次请求时动态生成。
    - **更安全：** 静态文件服务本身就更安全。
    
- **缺点：**
    - **内容更新不及时：** 除非重新构建和部署，否则内容不会更新。对于频繁变动的内容不适用。
    - **构建时间可能较长：** 如果有大量页面需要静态生成，构建时间会相应增加。
    
- **Next.js 中的使用场景：**
    - 博客文章、产品列表、文档、营销页面等内容不经常变动的页面。
    - 任何可以提前生成并对性能和 SEO 要求高的页面。

#### Pages Router 和新的 App Router 在实现SSG的差异
先在本地3001端口起一个node服务
- **Pages Router**：使用 `getStaticProps` 函数在构建时获取数据，并通过 `getStaticPaths` 指定需要预渲染的动态路径。
```tsx
// pages/blog/[id].tsx
import { InferGetStaticPropsType } from "next"

// 生成静态路径
export async function getStaticPaths() {
  const posts = await fetch('http://localhost:3001/api/posts'）
  const paths = posts.map((post) => ({
    params: { id: post.id.toString() },
  }))
  return { paths, fallback: 'blocking' }
}

// 获取静态属性
export async function getStaticProps({ params }: { params: { id: string } }) {
  const { id } = params 
  const post = await fetch('http://localhost:3001/api/posts'）
  return { props: { post, }, }
}

export default function PostPage({ post }: InferGetStaticPropsType<typeof getStaticProps>) {
  return (
    <div>
      <div>
        <h2>{post?.title}</h2>
        <p>{post?.content}</p>
      </div>
    </div>
  )
}
```
- **App Router**：使用 `generateStaticParams` 函数生成动态路由的参数，结合 React Server Components 实现数据获取和页面预渲染。
```tsx
// app/posts/[id]/page.tsx
export async function generateStaticParams() {
  const posts = await fetch('http://localhost:3001/api/posts', {
    cache: 'force-cache',
  })
    .then((res) => res.json())
  return posts.map((post: any) => ({
    id: post.id.toString(),
  }))
}

export default async function PostPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params
  const post = await fetch(`http://localhost:3001/api/posts/${id}`, {
    cache: 'force-cache',
  })
    .then((res) => res.json())
  return (
    <div>
      <div>
        <h2>{post?.title}</h2>
        <p>{post?.content}</p>
      </div>
    </div>
  )
}
```

渲染行为由 `fetch` 控制 (cache 无论是 `force-cache` 还是 `no-store` 在构建的时候都是会生成html, 呈现出来的区别主要是在页面刷新的时候，接口数据是否缓存)。

| `fetch` 选项                | 渲染模式            | 等价于 Pages Router 中              |
| ------------------------- | --------------- | ------------------------------- |
| `cache: "force-cache"`    | **SSG（静态生成）**   | `getStaticProps()`              |
| `next: { revalidate: N }` | **ISR（增量静态生成）** | `getStaticProps() + revalidate` |
| `cache: "no-store"`       | **SSR（服务端渲染）**  | `getServerSideProps()`          |

查看产物验证结果：
1. 通过运行 `pnpm build`， 可以在 `.next/server/app/blog` 目录下看到 `1.html/2.html` 文件
2. 导出静态站点产看out目录
在 `next.config.ts` 文件中配置
```ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
	output: 'export',
};
export default nextConfig;
```

运行 `pnpm build`，可以在根目录下看到输出目录 `out`, 并且存在 `blog/[1.html,2.html]`

### **3. 增量静态再生 (Incremental Static Regeneration - ISR)**

- **定义与工作原理 (使用 getStaticProps 的 revalidate 选项)：**
	- ISR 是静态生成（SSG）的一种增强方式。它允许你在**页面构建后**，在后台重新生成静态页面，而无需重新构建整个站点。
	- 在 App Router 中，你可以通过 `fetch` 时设置 `next.revalidate` 选项来启用 ISR：
		- `await fetch('https://example.com/api/data', {next: { revalidate: 60 }, // 每隔 60 秒重新生成页面});`
	- 当用户请求一个设置了 revalidate 的页面时：
		1. 如果页面已构建并且在 revalidate 时间内，则直接提供缓存的静态 HTML。
		2. 如果页面已构建但超过了 revalidate 时间，Next.js 仍然会先提供缓存的静态 HTML（保证快速响应），然后在后台尝试重新生成页面。如果生成成功，则会更新缓存，后续请求将获得新页面。
            
- **优点：**
    - **兼顾 SSG 的高性能和内容的相对新鲜度：** 用户总是能快速得到响应，同时内容也能在后台更新。
    - **无需重新构建整个站点即可更新内容。**
    - **按需生成 (On-demand ISR)：** Next.js 12.2+ 支持通过 API 按需重新生成特定页面，而不是等待 revalidate 时间。
	    - https://nextjs.org/docs/app/guides/incremental-static-regeneration#on-demand-revalidation-with-revalidatepath
        
- **缺点：**
    - **数据可能不是绝对实时的：** 在 revalidate 周期之间，用户看到的可能仍然是旧数据。
    - **首次访问过时页面的用户可能会触发再生(Regeneration)过程：** 虽然他们仍然会先看到旧内容。
        
- **Next.js 中的使用场景：**
    - 需要相对较新内容，但又能接受一定延迟的页面，例如热门新闻、电商商品详情（库存可能变化但不需要秒级更新）。
    - 拥有大量页面，不希望每次内容更新都重新构建整个站点的场景。
        
- **实践 (app 目录):**
```tsx
// app/blog/[id]/page.tsx
export default async function PostPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params
  const post = await fetch(`http://localhost:3001/api/posts/${id}`, {
    // cache: 'no-store', //no-store, force-cache, 
    next: { revalidate: 10,}
  })
    .then((res) => res.json())
  return (
    <div>
      <div>
        <h2>{post?.title}</h2>
        <p>{post?.content}</p>
      </div>
    </div>
  )
}
```
    
### **4. 服务端渲染 (Server-Side Rendering - SSR)**

- **定义与工作原理 (使用 getServerSideProps)：**
    - HTML 会在**每次请求时（request time）**动态生成。
    - 在 App Router 中，页面组件通过异步函数 `async function` 实现，并使用 `fetch()` 时设置 `cache: 'no-store'`（或使用 `export const dynamic = 'force-dynamic'`）来开启 SSR。
    - 每次用户请求该页面时，服务器会重新获取数据并生成完整的 HTML，然后发送给浏览器。
        
- **优点：**
    - **数据总是最新的：** 因为每次请求都会重新获取数据并生成页面。
    - **良好的 SEO：** 搜索引擎可以抓取到完整的、包含最新数据的 HTML 内容。
        
- **缺点：**
    - **性能相对 SSG/ISR 较慢：** 服务器需要在每次请求时都执行数据获取和页面渲染，TTFB (Time To First Byte) 通常比 SSG 长。
    - **服务器负载较高：** 需要更多的服务器资源来处理每个请求。
    -    **慢速数据源会阻塞页面渲染:** 如果数据获取较慢，整体页面响应也会变慢。
        
- **Next.js 中的使用场景：**
    - 页面内容需要高度个性化且数据频繁变化，例如用户个人资料页、需要实时数据的仪表盘。
    - 对 SEO 有要求，且内容必须是最新的页面。
    
- **实践(app 目录)**
```tsx
export default async function PostPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params
  const post = await fetch(`http://localhost:3001/api/posts/${id}`, {
    cache: 'no-store', //no-store, force-cache, 
  })
    .then((res) => res.json())
  return (
    <div>
      <div>
        <h2>{post?.title}</h2>
        <p>{post?.content}</p>
      </div>
    </div>
  )
}
```


### **5. React Server Components (RSC) 与 App Router 中的渲染**
Next.js 13 引入了 App Router (app 目录)，它建立在 React Server Components (RSC) 的基础上，带来了更细粒度的渲染和缓存控制。

**什么是 React Server Components？**
	- React Server Components（简称 RSC）允许你将组件放在服务端渲染，同时不增加客户端 JavaScript 体积。

**在 Next.js App Router 中：**
	- **默认所有组件为 Server Components**
	- **如果你想在客户端运行，必须显式加 `"use client"`**

- **Server Components (默认在 app 目录中):**
    - **定义与工作原理：** 在服务器上渲染，可以直接访问后端资源（如数据库、文件系统），并且它们的 JavaScript 代码**不会发送到客户端**。它们可以 async/await 数据获取，渲染结果 (RSC Payload，一种特殊的 JSON 格式) 被流式传输到客户端，由 React 在客户端进行重组和渲染。
        
    - **优点：**
        - **零客户端 JavaScript (默认)：** 大幅减少发送到客户端的 JS 包大小，提升初始加载性能。
        - **直接访问后端：** 简化数据获取逻辑，无需创建额外的 API 路由。
        - **自动代码分割：** 基于组件。
        - **流式渲染 (Streaming)：** 逐步显示 UI，提升感知性能。
            
    - **缺点/权衡：**
        - **不能使用浏览器 API：** 如 window, localStorage。
        - **不能使用 React Hooks：** 如 useState, useEffect (因为它们没有在客户端运行的 JS)。
        - 状态和交互需要 "Client Components"。
            
- **Client Components (使用 "use client"; 指令):**
    - **定义与工作原理：** 类似于传统的 React 组件，它们在客户端渲染 (或者在 SSR/SSG 模式下，先在服务器预渲染，然后在客户端 "hydrate")。它们可以使用 Hooks、浏览器 API，并处理用户交互。
    - **优点：** 拥有传统 React 组件的所有交互能力。
    - **缺点/权衡：** 它们的 JavaScript 代码会发送到客户端。
        
- **App Router 中的数据获取与缓存：**
    - Server Components 可以直接 async/await fetch(...)。Next.js 扩展了 fetch API，提供了自动的请求去重和灵活的缓存配置 (如 cache: 'force-cache', cache: 'no-store', next: { revalidate: seconds })。
    - 这使得你可以在组件级别控制数据的缓存行为，非常强大和灵活。
        
- **App Router 中的渲染模式：**
    - **默认静态：** App Router 中的 Server Components 默认是静态渲染的 (类似于 getStaticProps)。如果路由段不包含动态函数 (如 cookies(), headers()) 或动态数据获取 (如 fetch 使用 cache: 'no-store')，它会在构建时被静态渲染。
    - **动态渲染：** 当路由段使用动态函数或配置为不缓存的数据获取时，该路由段会在请求时在服务器上动态渲染 (类似于 getServerSideProps)。
    - **流式渲染 (Streaming) 与 Suspense：** App Router 很好地集成了 `<Suspense>`，允许你在数据加载时显示回退 UI，并在数据准备好后逐步流式传输和渲染内容，提升用户体验。
	    - https://nextjs.org/docs/app/guides/self-hosting#streaming-and-suspense


|模式|数据获取 & 渲染发生位置|HTML 生成时间|是否发送 JS|适用场景|
|---|---|---|---|---|
|**CSR**|客户端|浏览器运行时|✅ 全部发送|纯前端交互型应用|
|**SSR**|服务器|请求时|✅ 全部发送|数据实时更新，需 SEO|
|**SSG**|构建时在服务器|构建时|✅ 全部发送|内容少变，速度要求高的页面|
|**ISR**|构建时 + 后台更新|构建时 + 后台异步|✅ 全部发送|内容偶尔更新，但无需全站构建|
|**RSC**|数据和 UI 都在服务器|请求时（或预生成）|❌ 不发送部分组件的 JS|精细控制哪些逻辑运行在哪，提高性能

### 渲染模式对照表（Page Router vs App Router）

| 渲染模式             | Page Router 写法                     | App Router 写法                                                               |
| ---------------- | ---------------------------------- | --------------------------------------------------------------------------- |
| **静态生成 (SSG)**   | `getStaticProps`                   | `export const dynamic = "force-static"`或默认行为（无 fetch 请求）                    |
| **增量静态再生 (ISR)** | `getStaticProps` + `revalidate: n` | `export const revalidate = n`                                               |
| **服务端渲染 (SSR)**  | `getServerSideProps`               | `export const dynamic = "force-dynamic"`或使用 `cookies()` / `headers()` 等动态特性 |
| **客户端渲染 (CSR)**  | 无数据获取函数，组件中 `useEffect` 获取数据       | 放在 `client component` (`"use client"`) 中用 `useEffect()` 获取数据                |

在 App Router 中，Next.js 会根据你是否使用了动态数据（例如 fetch、headers、cookies）**自动推断渲染模式**。为了更**明确地控制渲染行为**，Next.js 提供了 `export const dynamic` 来手动指定。
#### 使用方式说明
```tsx
// app/page.tsx 或 app/posts/page.tsx
export const dynamic = 'force-static'
```

`dynamic` 说明, ***验证结果* 需要打包后运行 `pnpm start` 来启用构建产物**
- `force-static`
	- 在构建时（`next build`）生成 HTML 文件
	- 页面可以被 CDN 缓存，加载非常快
	- 所有数据必须是**静态可获取**的（如 `fetch` 带 `cache: 'force-cache'` 或使用本地 JSON）
	-  `fetch` 带 `cache: 'no-store'` 数据也不会改变
- `force-dynamic`
	- 页面会在**每次请求时重新生成**
	- 对于需要实时数据的页面（如用户相关、交易类数据）很合适
	-  使用 `force-cache` 的数据保持不变，其他接口可以动态响应
	- 禁用 HTML 缓存（即使使用静态资源，也不会缓存页面）
- `auto`
	- 默认行为
	- 如果页面中没有使用任何动态特性（如不带 `no-store` 的 fetch），会自动静态生成
	- 如果使用了不缓存的 `fetch` 或 `cookies()`, `headers()` 等，会自动启用 SSR

## `use client`/`use server` 区别

✅ 一句话理解

- `"use client"`：让该文件作为 **客户端组件**，可使用 `useState` 、`useEffect` 等 React Hook。
- `"use server"`：**可选指令**，明确标记该文件为 **服务器组件**（默认即是）。

🔍 区别详解

| 对比维度        | `"use client"`                                  | `"use server"`（或默认）            |
| ----------- | ----------------------------------------------- | ------------------------------ |
| **运行环境**    | 浏览器（客户端）                                        | Node.js（服务器端）                  |
| **默认行为**    | 非默认（必须显式声明）                                     | 默认行为（可不写 `"use server"`）       |
| **可用 Hook** | ✅ 可使用：`useState`, `useEffect`, `useRef` 等       | ❌ **不可使用** 任何 React 客户端 Hook   |
| **用途场景**    | - 表单交互<br>- 动画效果<br>- 使用 `localStorage`等浏览器 API | - 数据加载（如数据库查询）<br>- 渲染 HTML 结构 |
| **打包位置**    | 被打包发送到浏览器端                                      | 只存在于服务端，不发送给浏览器                |
| **与子组件关系**  | 可引入 **客户端和服务器组件**                               | 只能引入 **服务器组件**                 |
### 🧪 示例对比
✅ 客户端组件（必须加 `"use client"`）

```tsx
"use client"
import { Button } from '@/components/ui/button'
import { useState } from 'react'

export default function Counter() {
  const [count, setCount] = useState(0)
  return (
    <Button onClick={() => setCount(count + 1)}>
      Count: {count}
    </Button>
  )
}
```

✅ 服务端组件（默认）

```tsx
import Counter from "./components/Counter";

export default function Home() {
  return (
    <div className="flex flex-col gap-4 items-center">
      <main className="p-4">
        <Counter />
      </main>
    </div>
  );
}
```

- 页面组件默认是服务器组件。 
- 可以引入客户端组件，但自己不能使用 `useState`、`useEffect` 等。

`curl` 常用命令速查表

| **命令**          | **作用**                    | **示例**                           |
| --------------- | ------------------------- | -------------------------------- |
| `curl URL`      | 发送 GET 请求                 | `curl https://example.com`       |
| `-X METHOD`     | 指定请求方法（如 POST、PUT）        | `curl -X POST https://api.com`   |
| `-d`            | 发送 POST 数据（表单）            | `curl -d "a=1&b=2" URL`          |
| `-H`            | 设置请求头                     | `curl -H "Auth: Bearer xxx" URL` |
| `-F`            | 上传文件（multipart/form-data） | `curl -F "file=@a.jpg" URL`      |
| `-o 文件名`        | 下载并保存为指定文件                | `curl -o a.jpg URL`              |
| `-O`            | 下载并按原文件名保存                | `curl -O https://x.com/a.jpg`    |
| `-i`            | 显示响应头和响应体                 | `curl -i URL`                    |
| `-I`            | 仅获取响应头（HEAD 请求）           | `curl -I URL`                    |
| `-L`            | 自动跟随重定向                   | `curl -L URL`                    |
| `-A`            | 设置 User-Agent             | `curl -A "MyApp" URL`            |

| `--trace 文件`    | 输出详细日志到文件                 | `curl --trace trace.log URL`     |
